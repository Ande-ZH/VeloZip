# VeloZip 第一阶段实施计划（同前次提交内容，补充：构建/测试环境使用 F:/mc/env，缺项补入该目录）

## 0. 可行性结论（Phase 1-2，已完成源码研究）

**可以在现有 backend TCP 连接上安全切换 VeloZip framing，无需第二条隧道。** 已核实：Velocity 3.4.0（commit 6b1ea78）与 Purpur 26.1.2（MC 26.1.2，协议 775，Java 25）两端 backend pipeline 全部 handler 名称/顺序/压缩启用机制；两端均捆绑 Netty 4.2.7.Final；vanilla 帧边界不可能出现首字节 0x00（varint 长度 0 非法），0x00 magic 可作无歧义切换标记；Velocity PLAY↔CONFIG 会按类型引用 MinecraftVarintFrameDecoder（无 null 检查）→ 双模解码器必须继承父类；Purpur 状态切换只 replace decoder/encoder 名位，不动 splitter/prepender/compress。完整分析写入 docs/ANALYSIS.md。

## 1. 结构（Gradle Kotlin DSL 多模块）

velozip-common（纯 JDK17+Netty：protocol/compression/frame/authentication/metrics，配置模型）、velozip-velocity（Velocity340NetworkAdapter + compileOnly 内部类 stub）、velozip-backend（Purpur2612NetworkAdapter；优先尝试 repo.papermc.io 的 paper-server 工件，否则 stub）、velozip-benchmark（JMH 1.37）。shadowJar 产出 VeloZip-Velocity-0.1.0.jar 与 VeloZip-Backend-0.1.0.jar（common+zstd-jni 打入；zstd-jni 1.5.7-15 不 relocate；snakeyaml/HdrHistogram relocate；统一字节码 release=17，JDK 25 工具链编译）。

## 2. 协议设计

协商（PLAY 状态 plugin message `velozip:negotiate`，不碰 Login 状态机）：Velocity 在 ServerConnectedEvent 于 backend channel eventLoop 原子安装双模解码器并发 REQ（protoVer=1, zstd, level=1, 16B nonce, HMAC-SHA256(secret, nonce||参数)）→ Purpur 主线程校验（enabled、paper-global proxies.velocity.enabled、可选 IP allowlist、协议参数、HMAC）→ 通过则在 channel eventLoop 原子任务内装双模解码器、移除 compress/decompress/prepender、装 velozip 批量编码器（首帧 magic 即事实 ACK）；拒绝则回 REFUSE（vanilla 路径，Velocity 侧以注册 channel + PluginMessageEvent.setResult(handled) 拦截，绝不转发真实客户端）→ Velocity 收到首帧 magic 切换本端出站；REFUSE/5s 超时则还原 vanilla 并按 require-velozip 处理。时序安全性由 TCP 有序 + Netty eventLoop FIFO 保证，无双向不同步窗口。

帧格式：[magic 0x00 0x5A][ver=1][flags 0x01=ZSTD/0x02=RAW][varint payloadLen][varint origLen(ZSTD)][payload=完整 MC varint 帧拼接]。双模解码器帧边界检测 0x00 → 永久 VeloZip 模式；先验证长度（默认 max-frame-size 1MiB / max-uncompressed 2MiB）再分配；非法 magic/flags/长度/zstd 数据 → log + close 该连接。RAW 条件：batch < raw-threshold(128) 或 compressed ≥ original。

批量与 flush：出站编码器累计 write 到 pooled direct；≥ max-size(64KiB) 立即发；500µs 窗口（Velocity 每包 writeAndFlush、服务端每 send flush，字面 flush 触发会退化为 batch=1，故以窗口聚合、flush 记 pending）；emit = 复制到单个 direct → ZstdCompressCtx(level1, per-channel) compressDirectByteBuffer → 写帧 + 真实 flush；单包超限独立成帧；channelInactive 释放资源并 close ctx。压缩内联于 eventLoop，benchmark 验证 P99 后再考虑 executor（第一阶段不引入线程池）。

## 3. 注入点

Velocity（仅 backend channel）：frame-decoder → 双模子类；移除 compression-decoder/compression-encoder（或 frame-encoder）；addBefore minecraft-encoder 装 velozip 编码器。channel 经 ((ConnectedPlayer)player).getConnectedServer()/getConnectionInFlight() → VelocityServerConnection.getConnection() → MinecraftConnection.getChannel()/eventLoop()。Purpur：ChannelInitializeListenerHolder.addListener 标记 channel；协商成功时 splitter → 双模子类、移除 decompress/compress/prepender、addBefore encoder 装 velozip 编码器。VelocityCompressor 双 close 幂等性在 M0 核实。客户端链路零改动。

## 4. 配置/命令/日志/统计

两端 YAML 按 §16/§17 字段（algorithm/level 仅接受 zstd/1 否则启动报错；require-velozip 默认 false；secret 空=跳过认证但两端必须一致）；velocity 侧 servers.<name>.enabled 白名单；参数不一致拒绝启用并记录原因；require-velozip=true 时失败断开并日志（含 ServerPreConnectEvent 缓存拒绝）。/velozip status|stats（两端）：字节数/压缩比/帧统计/平均批大小/P50/P95/P99（HdrHistogram）/吞吐。日志按 §24。
